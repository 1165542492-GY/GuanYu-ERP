## 本轮目标

本轮 rc12 不做新业务功能，只做一次“真正打开页面的人机对话体验验收与补漏”。

目标是让普通员工一眼看懂：

1. 当前页面是做什么的
2. 现在该点哪个按钮
3. 保存成功还是失败
4. 失败原因是什么
5. 没权限该怎么办
6. 没数据该怎么办
7. 删除、关闭、作废、清空等危险操作会影响什么
8. 详情信息在哪里看
9. 不要出现技术英文、裸状态码、JSON 糊屏、[object Object]

## 重点检查

### 空数据

不能空白一片，要有清楚提示：

- 暂无数据，请点击“新增”创建第一条记录。
- 暂未查询到符合条件的记录，请调整筛选条件后再试。
- 当前账号没有权限查看此页面。

### 错误提示

不要直接出现：

- Error
- Failed
- Bad Request
- 403
- 409
- Exception
- object Object
- [object Object]
- JSON 一大串糊页面

### 删除确认

删除确认必须说清楚：

1. 删除哪条数据
2. 删除后能不能恢复
3. 如果被业务引用，不能直接删除

### 危险操作确认

例如：

- 关闭售后维修工单
- 作废单据
- 取消生产
- 导入覆盖
- 清空数据
- 重置密码
- 删除子账号

必须明确提示影响。

### 操作记录

继续确认：

- 默认 8 列
- 横向滚动减少
- IP / UserAgent / 长 ID / JSON 不在默认表格里撑爆
- 详情弹窗分区清楚
- 售后维修 SR 记录模块名显示“售后维修工单”
- 导出 CSV 保留
- 筛选保留
- 分页保留

### 售后维修工单

重点检查：

- 新增 / 编辑 / 删除 / 关闭 / 重新打开 / 生成应收 / 取消结算
- 操作确认文案是否清楚
- 审计摘要是否人话
- 操作记录是否能查到

## 修复原则

1. 能用全局函数统一修，就不要逐页乱贴重复代码
2. 能改文案解决，就不要改业务逻辑
3. 能轻量 CSS 解决，就不要大改页面结构
4. 不要追求花哨，只要清楚、稳、统一
5. 不要改库存、应收、应付、财务核心计算
6. 不要影响 rc11 已通过的回归
